## 一、3.0 演进目标与核心升级

### 1.1 核心痛点

V2.0 已实现四 Agent 闭环 + 教学方法论融合，但存在以下瓶颈：

| 痛点 | 现状 | 影响 |
|------|------|------|
| **路由僵硬** | 用户必须手动切换 Tab 才能用对应 Agent | 认知负担大，学习路径不连续 |
| **检索单一** | Doc Agent 仅靠向量相似度检索 | 关键词遗漏、召回不全、准确率不高 |
| **考试单薄** | 模拟考试只有单一场景+固定人格 | 考察维度单一，无法模拟真实工作 |
| **跨模块割裂** | Doc/Quiz/Persona/Scorer 各自为政 | 用户答错后需手动找学习资料、手动开练 |

### 1.2 V3.0 三大升级

```
┌─────────────────────────────────────────────────────────┐
│                    V3.0 三大核心升级                      │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  ① 高级检索管线                                         │
│     - 从单一向量检索 → 查询改写+多路召回+重排序+画像过滤 │
│     - 预计检索准确率提升 25-35%                          │
│     - 服务所有 Agent，知识供给更精准                    │
│                                                         │
│  ② 动态模拟考试系统                                     │
│     - 从单一场景 → 动态业务线切换 + 烦躁值双向波动        │
│     - 每场考试 10-15 轮对话，多业务线关联切换            │
│     - 综合评分 = 业务分60% + 情绪管理分25% + 效率分15%  │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 1.3 升级原则

1. **渐进增强**：V3.0 不推翻 V2.0，而是在其基础上叠加智能层
2. **降级兜底**：检索管线失败 → 回退到向量检索
3. **成本可控**：查询改写用一次 LLM 调用，重排序用本地模型
4. **可观测**：检索过程全链路日志，便于调优

## 三、高级检索管线

### 3.1 设计目标

从单一向量检索升级为"查询改写→多路召回→重排序→画像感知"的混合检索管线。

### 3.2 完整管线架构

```
用户查询："转账失败怎么处理？"
  ↓
┌──────────────────────────────────────────────┐
│           Step 1: 查询改写（Query Rewrite）    │
│                                              │
│  输入："转账失败怎么处理？"                     │
│  LLM改写输出：                                │
│  - 主查询："转账失败原因排查流程"               │
│  - 子查询1："转账失败 风控触发条件"             │
│  - 子查询2："转账失败 客户安抚话术"             │
│  - 子查询3："转账限额规则 超限处理"             │
│  意图标签：[业务流程, 风控规则, 话术]           │
└──────────────────────────────────────────────┘
  ↓
┌──────────────────────────────────────────────┐
│           Step 2: 多路召回（Multi-Recall）     │
│                                              │
│  ┌────────────┐  ┌────────────┐  ┌────────┐│
│  │ 向量检索    │  │ BM25检索   │  │图谱检索││
│  │(语义相似)   │  │(精确匹配)  │  │(关联)  ││
│  │Top-10      │  │Top-10      │  │Top-5   ││
│  └─────┬──────┘  └─────┬──────┘  └───┬────┘│
│        └───────────────┼──────────────┘     │
│                        ↓                    │
│              合并去重（25条→15条）            │
└──────────────────────────────────────────────┘
  ↓
┌──────────────────────────────────────────────┐
│           Step 3: 重排序（Reranking）         │
│                                              │
│  BGE Reranker 对15条候选逐一打分：             │
│  - 语义相关性（0-1）                           │
│  - 关键词覆盖率（0-1）                         │
│  - 业务权重（风控>话术>流程）                   │
│  最终排序 → Top-5                             │
└──────────────────────────────────────────────┘
  ↓
┌──────────────────────────────────────────────┐
│     Step 4: 画像感知过滤（Profile-Aware）      │
│                                              │
│  读取用户画像：                                │
│  - 费曼完成度 < 0.5 → 优先返回基础概念文档      │
│  - 费曼完成度 > 0.8 → 优先返回边界case和进阶    │
│  - 有"转账限额"弱点 → 强制包含限额规则文档       │
│  - 考试中"业务准确性"低 → 优先返回SOP文档       │
│  最终输出：Top-5 个性化文档                    │
└──────────────────────────────────────────────┘
  ↓
传递给 Doc Agent / Quiz Agent 作为上下文
```

### 4.3 技术选型

| 组件 | 技术 | 作用 | 部署方式 |
|------|------|------|---------|
| **查询改写器** | DeepSeek-V3 | 将口语化提问分解为结构化检索词 | 远程 API |
| **向量检索** | ChromaDB + BGE-M3 Embedding | 语义相似度检索，找"意思接近的" | 本地（已部署） |
| **BM25 检索** | Whoosh / Elasticsearch | 关键词精确匹配，找"字面匹配的" | 本地新增 |
| **知识图谱** | Neo4j（可选） | 实体关系检索，找"业务关联的" | 本地新增 |
| **重排序器** | BGE Reranker | 对多路召回结果统一打分排序 | 本地新增 |
| **画像过滤器** | 自研 | 根据用户画像调整最终结果 | 内嵌逻辑 |

#### 3.4.2 多路召回

```python
class MultiRecallRetriever:
    def __init__(self):
        self.vector_retriever = ChromaDBRetriever()  # 向量检索
        self.bm25_retriever = WhooshRetriever()       # BM25检索
        self.graph_retriever = Neo4jRetriever()       # 图谱检索（可选）

    async def retrieve(self, main_query: str, sub_queries: list, top_k: int = 10):
        # 并行多路召回
        vector_results = await self.vector_retriever.search(main_query, top_k=top_k)
        bm25_results = await self.bm25_retriever.search(main_query, top_k=top_k)
        graph_results = await self.graph_retriever.search(sub_queries, top_k=5) if self.graph_retriever else []

        # 合并去重
        all_results = vector_results + bm25_results + graph_results
        unique_results = self._deduplicate(all_results)
        return unique_results
```

#### 3.4.3 重排序器

```python
class BGEReranker:
    def __init__(self):
        self.model = self._load_bge_reranker()  # 本地部署

    def rerank(self, query: str, candidates: list, top_k: int = 5):
        scores = []
        for candidate in candidates:
            score = self.model.compute_score([
                {"query": query, "passage": candidate.content}
            ])
            # 综合得分 = 语义相关性 * 0.5 + 关键词覆盖率 * 0.3 + 业务权重 * 0.2
            final_score = (
                score * 0.5 +
                self._keyword_coverage(query, candidate) * 0.3 +
                self._business_weight(candidate.category) * 0.2
            )
            scores.append((candidate, final_score))

        scores.sort(key=lambda x: x[1], reverse=True)
        return [item[0] for item in scores[:top_k]]
```

#### 3.4.4 画像感知过滤

```python
class ProfileAwareFilter:
    def filter(self, candidates: list, user_profile: dict):
        feynman_progress = user_profile.get("feynman_progress", 0)
        weaknesses = user_profile.get("weaknesses", [])
        last_exam_dimensions = user_profile.get("last_exam_dimensions", {})

        filtered = []
        for candidate in candidates:
            # 费曼完成度低 → 优先基础概念
            if feynman_progress < 0.5 and candidate.difficulty == "advanced":
                continue
            # 费曼完成度高 → 优先进阶边界case
            if feynman_progress > 0.8 and candidate.difficulty == "basic":
                continue
            # 有弱点 → 强制包含相关文档
            if any(w in candidate.keywords for w in weaknesses):
                filtered.insert(0, candidate)  # 提到最前面
                continue
            filtered.append(candidate)

        return filtered[:5]
```

```

  ↓

  ↓

  ↓
```

## 四、动态模拟考试系统

### 4.1 设计目标

从"单一场景固定对话"升级为"动态业务线切换 + 烦躁值双向波动 + 目标导向考核"的真实客服场景模拟。

### 4.2 核心设计理念

```
考试本质：模拟真实客服工作流程，考察"业务能力 + 情绪管理 + 应变能力"三维度
核心机制：
- 知识点从知识库随机抽取，答案（踩分点）预存
- 动态烦躁值：答得好下降，答得差上升
- 业务线智能切换：基于关联图谱，而非纯随机
- 目标导向：每轮有业务目标，达成可提前推进
- 突发状况：10%概率注入，考察应变能力
```

### 4.3 考试流程设计

#### 4.3.1 考试初始化

```
考试开始
  ↓
【初始化阶段】
  1. 随机选择业务线（从知识库分类中抽取）
  2. 从该业务线随机选择1-2个知识点节点
  3. 加载知识点的踩分点（预存，避免反复查找）
  4. 随机选择客户人格（急躁/疑虑/普通）
  5. 设置初始烦躁值和阈值
  6. 设置业务目标（基于踩分点）
  7. 初始化最大轮数（10-15轮）
```

#### 4.3.2 知识点预存数据结构

```python
{
    "node_id": "node_023",
    "business_line": "转账业务",
    "category": "转账限额咨询",
    "title": "转账限额规则说明",
    "key_points": [
        {"point": "核实身份", "weight": 0.2, "keywords": ["身份证", "手机号", "验证", "确认"]},
        {"point": "解释限额规则", "weight": 0.3, "keywords": ["单笔5万", "日累计", "风控", "限额"]},
        {"point": "安抚情绪", "weight": 0.2, "keywords": ["抱歉", "理解", "帮您", "不便"]},
        {"point": "给出解决方案", "weight": 0.3, "keywords": ["调整限额", "柜台", "明日", "建议"]}
    ],
    "difficulty": "medium",
    "common_wrong_answers": ["系统故障", "网络问题", "不知道"],
    "related_business_lines": ["账户冻结", "信用卡业务"]
}
```

#### 4.3.3 业务线关联图谱

```
业务线关联关系（用于智能切换）：
转账业务 ←→ 账户冻结（风控关联）
转账业务 ←→ 信用卡业务（额度关联）
账户冻结 ←→ 司法查询（法律关联）
信用卡业务 ←→ 征信查询（信用关联）
密码重置 ←→ 账户安全（安全关联）
贷款业务 ←→ 征信查询（资质关联）

切换规则：
1. 本业务线目标全部达成 → 按关联图谱选下一业务线
2. 烦躁值超阈值 → 强制切换到"情绪安抚"环节（给考生挽回机会）
3. 烦躁值超阈值+无关联业务线 → 切换到完全不同业务线（考察应变）
```

#### 4.3.4 每轮对话流程

```
【第N轮对话】
  1. Persona Agent 根据当前业务线提问
     - 问题从预存知识点的场景描述生成
     - 客户语气随烦躁值动态变化

  2. 考生回答

  3. 评分：命中踩分点检测
     - LLM分析考生回答，匹配预存的key_points
     - 命中的踩分点权重累加 → 业务得分

  4. 烦躁值计算（双向波动）
     - 命中踩分点 → 烦躁值下降（根据权重）
     - 未命中/答非所问 → 烦躁值上升
     - 主动安抚情绪 → 额外下降
     - 给出错误信息 → 大幅上升

  5. 业务目标检查
     - 目标达成？→ 可切换下一业务线
     - 轮数超时？→ 烦躁值额外上升

  6. 突发状况检测（10%概率）
     - 触发则注入突发状况

  7. 结束条件检查
     - 烦躁值达100 → 客户挂断，考试失败
     - 轮数达上限 → 考试结束
     - 所有业务线目标达成 → 考试提前结束
```

### 4.4 烦躁值机制（核心设计）

#### 4.4.1 人格与烦躁值配置

| 人格类型 | 初始烦躁值 | 阈值 | 特点 |
|---------|-----------|------|------|
| **急躁型** | 60 | 80 | 情绪波动大，容易不耐烦 |
| **疑虑型** | 40 | 70 | 持续怀疑，容易不信任 |
| **普通型** | 20 | 85 | 情绪平稳，要求合理 |
| **愤怒型** | 70 | 75 | 情绪极度不稳定（高难度） |

#### 4.4.2 烦躁值上升场景

| 触发条件 | 上升幅度 | 说明 |
|---------|---------|------|
| 答非所问 | +15 | 完全没理解客户问题 |
| 术语堆砌听不懂 | +10 | 使用专业术语过多 |
| 重复问相同问题 | +12 | 客户已经说过但考生没记住 |
| 态度生硬 | +8 | 缺乏礼貌用语 |
| 给出错误信息 | +20 | 提供错误的业务信息 |
| 轮数超时未完成目标 | +10 | 效率低下 |
| 客户电话被打断 | +5 | 突发状况影响 |

#### 4.4.3 烦躁值下降场景（核心改进）

| 触发条件 | 下降幅度 | 说明 |
|---------|---------|------|
| 主动安抚情绪 | -15 | 使用"抱歉""理解""给您带来不便"等话术 |
| 表达同理心 | -12 | "我理解您的心情""换做是我也会着急" |
| 给出清晰解决方案 | -10 | 明确告诉客户怎么做 |
| 确认客户理解 | -8 | "您清楚了吗""还有什么疑问" |
| 主动追问需求 | -5 | "请问还有什么可以帮您" |
| 命中关键踩分点 | -5~-10 | 根据权重 |

#### 4.4.4 烦躁值影响客户行为

| 烦躁值区间 | 客户行为描述 | 示例话术 |
|-----------|------------|---------|

### 4.7 综合评分体系

#### 4.7.1 评分公式

```
最终评分 = 业务分（60%）+ 情绪管理分（25%）+ 效率分（15%）
```

#### 4.7.2 业务分

```python
业务分 = Σ（各业务线踩分点命中率 × 业务线权重）

踩分点命中率 = 命中的踩分点权重之和 / 所有踩分点权重之和
业务线权重 = 业务线难度系数（初级1.0、中级1.2、高级1.5）
```

#### 4.7.3 情绪管理分（核心改进）

```python
情绪管理分 = 基础分（60分）+ 烦躁值净下降奖励 + 超阈值惩罚

烦躁值净下降奖励：
- 烦躁值下降 > 30 → +25分
- 烦躁值下降 20-30 → +15分
- 烦躁值下降 10-20 → +5分
- 烦躁值下降 ≤ 10 → +0分

超阈值惩罚：
- 烦躁值曾超阈值 0 次 → +0分
- 烦躁值曾超阈值 1 次 → -10分
- 烦躁值曾超阈值 2 次 → -20分
- 触发挂断（烦躁值达100）→ 该项0分

示例：
初始烦躁值60，最终烦躁值35（净下降25），超阈值0次
情绪管理分 = 60 + 15 + 0 = 75分
```

#### 4.7.4 效率分

```python
效率分 = 基础分（60分）+ 完成度奖励 + 轮数奖励

完成度奖励：
- 完成业务线数 / 预设业务线数 × 20分

轮数奖励：
- 实际轮数 ≤ 预期轮数 → +20分
- 实际轮数 = 预期轮数 + 2 → +10分
- 实际轮数 > 预期轮数 + 2 → +0分

示例：
预设3条业务线，实际完成2条，实际轮数10（预期12）
效率分 = 60 + (2/3 × 20) + 20 = 60 + 13.33 + 20 = 93.33分
```

#### 4.7.5 突发状况附加分

```python
突发状况附加分（上限+10分）：
- 成功处理1次突发状况 → +3分
- 成功处理2次突发状况 → +7分
- 成功处理3次及以上 → +10分
- 处理失败 → -5分/次
```

```
考试开始
  ↓
【初始化】
  - 随机选业务线A
  - 加载业务线A的踩分点（预存）

  - 设置业务目标（2-3个）
  - 设置最大轮数（10-15轮）
  ↓

  - Persona Agent 根据业务线A提问（语气随烦躁值变化）
  - 考生回答
  - 评分：命中踩分点检测
  - 烦躁值计算（双向波动）
  - 检查：业务目标达成？烦躁值超阈值？
  ↓
【第2-15轮对话】（循环）
  ├─ 业务目标达成 → 按关联图谱切换业务线，加载新踩分点
  ├─ 烦躁值超阈值 → 强制情绪安抚环节（给挽回机会）
  ├─ 烦躁值达100 → 客户挂断，考试失败（情绪管理分0）
  ├─ 10%概率 → 突发状况注入，考察应变能力
  ├─ 轮数超时 → 烦躁值额外上升
  └─ 轮数达上限 或 所有业务线完成 → 考试结束
  ↓
【考试结束】
  - 计算综合评分（业务分60% + 情绪管理分25% + 效率分15%）
  - 生成能力画像更新
  - 记录弱点标签
  - 推荐反向训练
  - 生成详细考试报告
```

### 4.11 评分与学习闭环

#### 4.11.1 弱点标签生成

```python
async def generate_weakness_tags(exam_record: DynamicExam):
    """根据考试结果生成弱点标签"""
    tags = []
    
    # 根据各维度得分生成标签
    if exam_record.business_score < 70:
        tags.append({"tag": "业务知识薄弱", "dimension": "business"})
    
    if exam_record.emotion_score < 70:
        tags.append({"tag": "情绪管理不足", "dimension": "emotion"})
    
    # 根据未命中的踩分点生成标签
    for line in exam_record.business_lines_covered:
        if not line["completed"]:
            for goal in line["goals"]:
                if goal not in line["goals_completed"]:
                    tags.append({
                        "tag": f"{line['business_line']} - {goal['name']}",
                        "dimension": "business",
                        "node_id": line["node_ids"][0]
                    })
    
    # 根据烦躁值峰值生成标签
    if exam_record.max_anxiety >= exam_record.anxiety_threshold:
        tags.append({"tag": "客户情绪控制能力", "dimension": "emotion"})
    
    return tags
```

#### 4.11.2 学习闭环

```
考试结束 → 生成弱点标签 → 存入 user_weaknesses 表
  ↓
Quiz Agent 生成反向训练题（基于弱点标签）
  ↓
Doc Agent 推荐相关知识点复习
  ↓
考生完成反向训练 → 验证修正结果 → 更新能力画像
```

## 五、高级检索管线应用场景

### 5.1 场景价值

| 场景 | 当前问题 | 高级管线解决方式 | 预期提升 |
|------|---------|----------------|---------|
| **Doc Agent 知识问答** | 语义检索可能漏掉关键词匹配 | 查询改写 + 向量+BM25多路召回 | 召回率 +30% |
| **Quiz Agent 出题素材** | 出题素材太泛 | 检索完整业务流程作为出题上下文 | 题目质量 +25% |
| **Persona Agent 对话** | 客户回复业务细节不准确 | 实时检索注入对话上下文 | 真实感 +40% |
| **Scorer Agent 评分** | 无法判断是否合规 | 检索标准 SOP 作为评分参考 | 评分准确度 +20% |
| **反向训练出题** | 题目偏离实际业务 | 检索相关业务文档作为出题素材 | 针对性 +35% |
| **费曼复述评估** | 无法精准识别遗漏点 | 检索完整知识点对比复述内容 | 遗漏识别 +50% |
| **动态考试场景选取** | 场景选取随机 | 根据用户画像检索合适难度的场景 | 个性化 +45% |

## 十、总结

V3.0 的三大升级让系统从"能用"迈向"好用"：

1. **LLM 语义路由**：让系统"理解"用户，而非"匹配"关键词，实现真正的智能调度
2. **高级检索管线**：让知识"找得准"，而非"找得到"，提升所有 Agent 的知识供给质量
3. **多轮多场景考试**：让考试"像真实工作"，而非"像做题"，全面考察综合能力

三者协同形成完整闭环：**智能路由理解需求 → 高级检索精准供给 → 多轮考试综合考察 → 画像更新反馈路由**，构建真正意义上的"智能陪练"。
