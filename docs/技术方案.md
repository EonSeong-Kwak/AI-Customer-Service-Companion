**🎯 PBL项目制实现**：
```python
class CustomerIntentManager:
    def __init__(self):
        self.intent_stack = []
        self.current_intent = None

    def switch_intent(self, new_intent):
        if self.current_intent:
            self.intent_stack.append(self.current_intent)
        self.current_intent = new_intent

    def get_context(self):
        return {
            "current": self.current_intent,
            "history": self.intent_stack
        }

class ProjectBasedPersona:  # 新增项目制管理
    def __init__(self, project_config):
        self.project = project_config
        self.current_task = 0
        self.task_progress = []

    def check_task_completion(self, conversation_history):
        """检查当前任务是否完成"""
        task = self.project['tasks'][self.current_task]
        prompt = f"""
        任务：{task['name']}
        成功标准：{task['success_criteria']}
        对话历史：{conversation_history}
        请判断：是否完成当前任务？
        输出格式：{{'completed': true/false, 'score': 0-100, 'feedback': '...'}}
        """
        return llm.call(prompt)

    def switch_to_next_task(self):
        """切换到下一个任务"""
        self.current_task += 1
        if self.current_task < len(self.project['tasks']):
            new_task = self.project['tasks'][self.current_task]
            return self.inject_intent(new_task)
        else:
            return "project_completed"
```

## 七、关键设计原则

```
1. 角色权限分离
   管理员负责配置和内容管理，考生只能使用系统
   人格配置、题库编辑、评分规则等核心配置仅管理员可操作

2. 标准答案预绑定
   出题时即生成答案，评分时直接读取，不依赖实时检索

3. 人格配置化
   所有人格以yaml配置驱动，管理员新增人格不改代码

4. 意图状态机兜底
   话题跳跃行为由状态机 + 代码层强控，不完全依赖模型

5. 模型统一远程API
   全部模块均调用远程API，避免本地部署大模型的硬件依赖，降低运维复杂度

6. RAG边界清晰
   知识库只在Doc Agent和Quiz Agent中是核心
   Persona Agent辅助可选，Scorer Agent评分不依赖RAG

7. 纵向追踪
   每次考试结果自动存储，支持考生个人成长曲线和团队能力热力图

8. 教学方法论深度融合
   费曼学习法、番茄工作法、PBL项目制、反循环机制贯穿各Agent
   从"单一问答"升级为"理解-节奏-实战-修正"完整学习闭环
```

### 📖 费曼学习法 → Doc Agent & Quiz Agent

**核心理念**：通过"教会别人"检验理解，发现盲点

**融入方式**：
```
传统流程: 学习 → 提问 → 检索答案
费曼流程: 学习 → 复述知识点(用自己的话解释) → Agent判断理解度
        → 发现盲点 → 针对性推荐复习 → 再次验证
```

**Doc Agent 实现**：
- 新增"费曼复述模式"：考生学习完知识点后，点击"用自己的话复述"
- Prompt 示例：

原始知识点：{original_node}
请判断：
1. 核心概念是否准确？（是/否）
2. 是否遗漏关键细节？
3. 理解度评分：0-100
4. 推荐复习内容：{recommended_sections}"
```
- 系统追踪费曼完成度：
```
学习(30%) → 复述(50%) → 盲点识别(70%) → 复习验证(100%)
```

**Quiz Agent 实现**：
- 新增"教学题型"：考生需要向一个"不懂的客户"解释清楚业务流程
- 出题 Prompt：
```

### 🔄 反循环机制 → Quiz Agent & Scorer Agent

**核心理念**：错误是新一轮学习的起点，建立"错→析→改→验"闭环

**融入方式**：
```
当前系统: 答错 → 显示正确答案 → 继续
反循环:   答错 → 反向分析环节(让考生解释为何错)
              → 生成针对性反向训练题
              → 验证是否真正掌握
              → 若仍错，触发强化学习模式(返回Doc Agent)
```

#### 4.1 LLM语义路由升级（技术方案3.0核心）

**目标**：从硬编码路由升级为智能语义路由，实现"理解意图→个性化推荐→自动路由"的智能调度

**核心价值**：
- 理解用户真实意图，而非简单关键词匹配
- 结合用户画像（费曼进度、反循环成功率、能力画像）做个性化路由
- 从"被动响应"升级为"主动理解"
- 统一入口，消除用户"不知道该用哪个功能"的认知负担

**技术选型**：
- Semantic Router（开源库）：基于向量相似度的意图分类
- 或自建语义路由（结合DeepSeek-V3）：更灵活，支持复杂决策
- 用户画像数据源：费曼完成度、弱点标签、番茄钟节奏、能力画像四维分数

**架构设计**：
```
用户输入
  ↓
┌──────────────────────────────────────────────┐
│           LLM 语义路由层                       │
│                                              │
│  1. 意图识别（Intent Classification）          │
│     - 学习意图 → Doc Agent                    │
│     - 练习意图 → Quiz Agent                   │
│     - 考试意图 → Persona Agent                │
│     - 查询意图 → 查看报告/趋势/能力画像         │
│     - 求助意图 → 反向训练/强化学习              │
│                                              │
│  2. 画像感知（Profile-Aware Routing）          │
│     - 读取费曼完成度 → 判断理解深度             │
│     - 读取弱点标签 → 判断薄弱领域               │
│     - 读取番茄钟节奏 → 判断学习状态             │
│     - 读取能力画像 → 判断综合水平               │
│                                              │
│  3. 个性化决策（Personalized Decision）        │
│     - 理解度低 + 有弱点 → 强制推送反向训练       │
│     - 理解度高 + 无弱点 → 推荐教学题型挑战       │
│     - 连续学习过久 → 建议休息                   │
│     - 考试分数低 → 推荐Doc Agent复习            │
└──────────────────────────────────────────────┘
  ↓
目标 Agent + 上下文参数（用户画像快照）
```

**应用场景详解**：

| 场景 | 用户输入 | 语义路由决策 | 执行路径 |
|------|---------|-------------|---------|
| **模糊学习需求** | "我感觉客户情绪安抚这块不太会" | 识别为"学习需求" + 情绪安抚弱点 → 费曼完成度0.65判断"理解不深" | Doc Agent + 推荐情绪安抚知识点 + 记录薄弱点 |
| **练习后求助** | "这道题我答得不好，怎么办" | 识别为"求助意图" + 关联最近练习记录 + 提取弱点 | Quiz Agent生成反向训练题 + 触发反循环闭环 |
| **考试后复盘** | "我上次考试哪方面比较差" | 识别为"查询意图" + 读取考试历史 + 能力画像 | 返回趋势分析 + 推荐针对性练习 |
| **学习节奏异常** | "今天学什么" | 识别为"学习需求" + 读取番茄钟数据 → 连续学习3小时 | 建议休息 + 推荐轻松的费曼复述 |
| **跨模块联动** | "帮我复习一下之前答错的" | 识别为"练习意图" + 读取弱点标签 → 未解决弱点3个 | Quiz Agent推送反向训练 + 关联Doc Agent知识点 |
| **能力评估请求** | "我现在的水平怎么样" | 识别为"查询意图" + 触发能力画像生成 | 返回四维能力雷达图 + 个性化提升建议 |

**语义路由 vs 硬编码路由对比**：

| 维度 | 硬编码路由（当前） | LLM语义路由（3.0） |
|------|-----------------|-------------------|
| 意图识别 | 关键词匹配（"练习"→Quiz） | 语义理解（"我答得不好"→求助→反向训练） |
| 个性化 | 无（所有用户相同路径） | 基于画像差异化路由 |
| 跨模块联动 | 无（用户手动切换Tab） | 自动跨Agent调度 |
| 主动推荐 | 无（被动等待用户操作） | 主动识别需求并推送 |
| 扩展性 | 新增功能需改前端代码 | 新增意图只需配置路由规则 |

#### 4.2 高级检索管线升级（技术方案3.0核心）

**目标**：从单一向量检索升级为"查询改写→多路召回→重排序→画像感知"的混合检索管线

**核心价值**：
- 提升知识检索准确率（预计提升20-30%）
- 支持查询改写、多路召回、重排序
- 根据用户画像动态调整检索策略（新手多检索基础概念，熟手多检索边界case）
- 解决当前"检索不准→答案跑偏→用户不信任"的问题

**技术选型**：
- 混合检索：向量检索（ChromaDB） + BM25关键词检索（Elasticsearch/Whoosh）
- 重排序：BGE Reranker（开源，本地部署，支持中英文）
- 查询改写：DeepSeek-V3（将口语化提问改写为结构化检索词）
- 知识图谱：Neo4j（可选，存储银行业务实体关系）

**完整检索管线架构**：
```
用户查询："转账失败怎么处理？"
  ↓
┌──────────────────────────────────────────────┐
│           Step 1: 查询改写（Query Rewrite）    │
│                                              │
│  输入："转账失败怎么处理？"                     │
│  LLM改写输出：                                │
│  - 主查询："转账失败原因排查流程"               │
│  - 子查询1："转账失败 风控触发条件"             │
│  - 子查询2："转账失败 客户安抚话术"             │
│  - 子查询3："转账限额规则 超限处理"             │
│  意图标签：[业务流程, 风控规则, 话术]           │
└──────────────────────────────────────────────┘
  ↓
┌──────────────────────────────────────────────┐
│           Step 2: 多路召回（Multi-Recall）     │
│                                              │
│  ┌────────────┐  ┌────────────┐  ┌────────┐│
│  │ 向量检索    │  │ BM25检索   │  │图谱检索││
│  │(语义相似)   │  │(精确匹配)  │  │(关联)  ││
│  │Top-10      │  │Top-10      │  │Top-5   ││
│  └─────┬──────┘  └─────┬──────┘  └───┬────┘│
│        │               │              │     │
│        └───────────────┼──────────────┘     │
│                        ↓                    │
│              合并去重（25条→15条）            │
└──────────────────────────────────────────────┘
  ↓
┌──────────────────────────────────────────────┐
│           Step 3: 重排序（Reranking）         │
│                                              │
│  BGE Reranker 对15条候选逐一打分：             │
│  - 语义相关性（0-1）                           │
│  - 关键词覆盖率（0-1）                         │
│  - 业务权重（风控>话术>流程）                   │
│  最终排序 → Top-5                             │
└──────────────────────────────────────────────┘
  ↓
┌──────────────────────────────────────────────┐
│     Step 4: 画像感知过滤（Profile-Aware）      │
│                                              │
│  读取用户画像：                                │
│  - 费曼完成度 < 0.5 → 优先返回基础概念文档      │
│  - 费曼完成度 > 0.8 → 优先返回边界case和进阶    │
│  - 有"转账限额"弱点 → 强制包含限额规则文档       │
│  - 考试中"业务准确性"低 → 优先返回SOP文档       │
│  最终输出：Top-5 个性化文档                    │
└──────────────────────────────────────────────┘
  ↓
传递给 Doc Agent / Quiz Agent 作为上下文
```

**应用场景详解**：

| 场景 | 用户查询 | 当前检索问题 | 高级检索管线解决方式 |
|------|---------|-------------|-------------------|
| **Doc Agent 知识问答** | "密码锁了怎么办" | 仅返回语义相似文档，可能漏掉"取款密码vs登录密码"的区别 | 查询改写为"密码锁定 解锁流程 取款密码 登录密码" → 多路召回覆盖更全 → 重排序优先返回区分两种密码的文档 |
| **Quiz Agent 出题素材** | 基于"信用卡挂失"出题 | 检索到的知识点可能太泛，出题质量不高 | 查询改写为"信用卡挂失 临时挂失 正式挂失 盗刷SOP 新卡绑定" → 多路召回确保覆盖完整流程 → 重排序优先返回SOP文档 |
| **Persona Agent 背景知识** | 客户提到"跨境转账" | Persona可能回复不准确业务细节 | 实时检索"跨境转账 限额 手续费 到账时间" → 注入Persona的对话上下文 → 客户说法更真实 |
| **Scorer Agent 评分参考** | 考生回答涉及"司法冻结" | 评分时可能无法判断是否合规 | 检索"司法冻结 全额冻结 限额冻结 解冻流程" → 作为评分参考依据 → 评分更准确 |
| **反向训练题生成** | 基于弱点"审批透明化"出题 | 生成的题目可能偏离实际业务 | 检索"审批流程 透明化 客户告知义务" → 作为出题素材 → 题目更贴合实际 |
| **费曼复述评估** | 学员复述"账户受控排查" | 评估时无法判断是否遗漏关键点 | 检索完整知识点 → 对比复述内容 → 精准识别遗漏点 |

**检索管线各组件说明**：

| 组件 | 技术 | 作用 | 部署方式 |
|------|------|------|---------|
| **查询改写器** | DeepSeek-V3 | 将口语化提问分解为结构化检索词 | 远程API |
| **向量检索** | ChromaDB + BGE-M3 Embedding | 语义相似度检索，找"意思接近的" | 本地（已部署） |
| **BM25检索** | Whoosh / Elasticsearch | 关键词精确匹配，找"字面匹配的" | 本地新增 |
| **知识图谱** | Neo4j（可选） | 实体关系检索，找"业务关联的" | 本地新增 |
| **重排序器** | BGE Reranker | 对多路召回结果统一打分排序 | 本地新增 |
| **画像过滤器** | 自研 | 根据用户画像调整最终结果 | 内嵌逻辑 |

**与现有系统的集成方式**：
- Doc Agent：当前 `external_kb.search()` 升级为调用完整管线
- Quiz Agent：出题前先走管线检索素材，提升题目质量
- Persona Agent：对话中实时检索，增强客户回复的真实性
- Scorer Agent：评分时检索标准SOP，提升评分准确性

#### 4.4 本地微调模型（替代部分远程API）

随着系统积累足够的银行领域对话数据，可针对高频调用模块进行本地微调，降低长期 API 成本。

**微调目标模型**：优先对 Persona Agent 和 Scorer Agent 使用的模型进行微调，因为这两个模块调用频率最高、领域专用性最强。

**微调流程**：

| 步骤 | 内容 |
|------|------|
| **① 数据收集** | 从系统运行中积累真实的考生对话记录、人工标注的评分结果，形成有监督训练数据集 |
| **② 数据清洗** | 过滤低质量对话、标准化评分标注格式，按人格类型和业务场景分类整理 |
| **③ 选择基座模型** | 选用参数量适中的开源模型（如 Qwen2.5-7B / ChatGLM3-6B），在银行合规约束下可部署于私有服务器 |
| **④ SFT 微调** | 使用 LoRA / QLoRA 方式进行参数高效微调，减少显存需求；Persona Agent 侧重人格一致性和意图切换数据，Scorer Agent 侧重评分准确性数据 |
| **⑤ 评估与对比** | 微调后模型与原远程 API 在评分一致性、人格拟真度两个维度上进行 A/B 测试，达标后再切换 |
| **⑥ 本地部署** | 通过 Ollama 或 vLLM 在私有服务器上提供推理服务，对外接口与远程 API 保持一致，业务层无感切换 |

**预期收益**：
- 高频模块 API 调用成本降低 60%~80%
- 数据不出内网，满足银行业数据合规要求
- 模型可针对机构自身业务话术持续迭代优化

## 十、LlamaIndex 与 LangChain 在各模块的使用说明

### 框架核心差异

| 维度 | LlamaIndex | LangChain |
|------|-----------|-----------|
| **核心定位** | 专注文档索引与 RAG 检索，做好"存-取-问"这条线 | 通用 AI 应用编排框架，擅长 Chain / Agent / Tool 的组合调度 |
| **最强场景** | 大量非结构化文档的语义检索、知识库构建 | 多步骤对话流程、Function Calling、多工具调用 |
| **数据流向** | 文档 → 解析 → 分块 → Embedding → 向量库 → 检索返回 | 用户输入 → Chain → 调用工具/LLM → 输出结果 |

---

### 📚 Doc Agent — 使用 LlamaIndex

**为什么用 LlamaIndex？**
Doc Agent 的核心任务是"把 PDF 变成可检索的知识库"，这正是 LlamaIndex 的主战场。LlamaIndex 内置了完整的文档处理管线，从解析、分块、Embedding 到写入向量库，都有现成的抽象层，无需手动拼接。

**具体承担的工作：**
- **文档解析与分块**：管理员上传 PDF 后，LlamaIndex 自动完成格式解析和按段落/语义分块，保留页码、章节等元数据
- **构建向量索引**：调用 Embedding 模型将文本块向量化，统一写入 Milvus / Chroma，并维护文档与向量节点的映射关系
- **语义检索问答**：考生提问时，LlamaIndex 的 `QueryEngine` 自动完成"语义检索 → 召回 Top-K 节点 → 拼装 Prompt → 调用 Qwen-Long 生成答案"全流程，对外只暴露一个查询接口

**总结**：Doc Agent 几乎不需要自己写 RAG 逻辑，LlamaIndex 把整条 RAG 链路封装好了，直接配置调用即可。

---

### 🏋️ Quiz Agent — 使用 LangChain

**为什么用 LangChain？**
Quiz Agent 的任务不是单纯检索，而是一个多步骤流程：先从向量库检索知识节点，再将节点内容作为素材驱动 LLM 出题，再将生成的题目存入题库。这种"检索 → 推理 → 结构化输出"的链式编排是 LangChain 的强项。

**具体承担的工作：**
- **RetrievalQA Chain（出题）**：将用户选择的专题作为查询词，先从向量库（复用 Doc Agent 建好的索引）检索最相关的知识节点，再将节点内容填入出题 Prompt，驱动 DeepSeek-V3 生成情景题、标准答案和关键得分点
- **LLM Chain（答案评估）**：考生提交答案后，直接将"标准答案 + 考生答案"拼入评估 Prompt，不再检索，由 LLM 从准确性和完整性两个维度打分并给出反馈
- **结构化输出控制**：通过 LangChain 的输出解析器约束 LLM 输出为固定 JSON 格式，便于写入题库 DB

**总结**：Quiz Agent 用 LangChain 把"检索"和"生成"两步串成一条 Chain，同时能方便地控制输出结构，比直接裸调 LLM API 更健壮。

### 🎭 Persona Agent — 使用 LangChain

**为什么用 LangChain？**
Persona Agent 的核心是**多轮对话状态管理**和**动态 Prompt 注入**，而不是文档检索。LangChain 的 `ConversationChain` 和 Memory 模块天然支持对话历史维护，与自定义的意图状态机可以直接集成。

**具体承担的工作：**
- **对话历史管理**：LangChain 的 Memory 组件负责维护多轮对话上下文，每轮对话自动追加历史，不需要手动拼接 message list
- **动态 Prompt 构建**：每一轮都需要将"当前人格规则 + 当前意图 + 意图切换历史 + 对话历史 + 考生最新输入"拼装成完整 Prompt，LangChain 的 `PromptTemplate` 支持变量动态注入，配合意图状态机（自定义 Python 类）提供的上下文数据使用
- **行为触发集成**：当状态机判断需要强制切换意图时，将新意图状态注入 LangChain 的下一轮 Prompt 变量中，驱动 Doubao-32k 生成对应人格行为的回复

**总结**：Persona Agent 的重点不在 RAG，在于多轮状态流转。LangChain 负责对话链路的"管道"，自定义意图状态机负责"人格逻辑"，两者分工明确。

### 📊 Scorer Agent — 使用 LangChain Function Calling

**为什么用 LangChain？**
Scorer Agent 的评分过程不依赖知识库检索（答案已预绑定），核心是"约束 LLM 输出结构化评分 JSON"以及"调用工具函数写入报告、推荐复习节点"，这正是 LangChain Function Calling 的典型场景。

**具体承担的工作：**
- **结构化评分输出**：通过 LangChain 的 Function Calling / OutputParser，要求 DeepSeek-V3 严格按照预定义的 JSON Schema 输出各维度分数和薄弱点列表，避免自由格式输出导致解析失败
- **工具函数绑定**：将 `save_score_report()`、`recommend_nodes()`、`track_progress()` 等函数注册为 LangChain Tool，LLM 在评分后自动触发调用，将结果写入存储层
- **薄弱点推荐回流**：评分完成后，根据 LLM 识别的薄弱维度，调用工具查询向量库（Doc Agent 的知识节点），将推荐复习内容一并返回给考生

**总结**：Scorer Agent 用 LangChain 把"LLM评分"和"写报告/推荐节点"等后续动作串联成一个自动化流程，Function Calling 保证输出格式可靠、动作可预期。

### 🔀 Orchestrator — 使用 LangGraph

**为什么用 LangGraph？**
Orchestrator 需要根据用户请求动态决策"该调哪个 Agent"，并在 Agent 之间传递状态，这是一个有向图结构的工作流，不是线性 Chain。LangGraph 专门为此设计，支持条件分支、循环、状态持久化。

**具体承担的工作：**
- **节点定义**：每个 Agent（Doc / Quiz / Persona / Scorer）作为图中的一个节点，Orchestrator 自身也是一个路由节点
- **条件路由**：根据用户角色（admin/trainee）和请求类型，通过图的边（Edge）条件判断流向哪个 Agent 节点
- **状态传递**：LangGraph 的 State 对象在节点间流转，携带"当前用户身份、本轮任务类型、上游 Agent 输出"等信息，下游 Agent 从 State 中读取所需上下文
- **远程API驱动**：路由判断逻辑由 DeepSeek-V3 远程API完成，通过精简的路由 Prompt 控制输出，只需返回目标 Agent 名称，调用成本可控

**总结**：LangGraph 让 Orchestrator 的路由逻辑从"一堆 if-else"变成可视化的有向图，状态管理更清晰，后续扩展新 Agent 只需添加新节点和边，不动原有逻辑。
