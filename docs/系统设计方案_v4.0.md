## 技术点说明

### 1. WebSocket vs SSE

**技术方案要求WebSocket，实际用SSE替代。**

| 对比项 | WebSocket | SSE（当前实现） |
|-------|-----------|----------------|
| 通信方向 | 双向（服务端可主动推送） | 单向（服务端→客户端） |
| 断线重连 | 需手动实现 | 浏览器自动重连 |
| 适用场景 | 需要客户端也发消息的场景 | 只需服务端推送的场景 |

**具体例子**：
```
场景：动态考试中，客户烦躁值≥80需强制挂断

【WebSocket方案】
服务端检测到烦躁值≥80 → 主动推送 {"event": "hangup"}
前端收到 → 立即显示挂断提示

【SSE方案（当前）】
服务端检测到烦躁值≥80 → 在下一次流式返回中带 {"hangup": true}
前端轮询检查 → 发现后显示挂断
（需要等下一次请求才能触发，但实际体验差异很小）
```

**结论**：对于LLM流式输出场景，SSE完全够用，不需要WebSocket的双向能力。

---

### 2. Ant Design X vs Ant Design 5.x

**技术方案提及Ant Design X，实际用标准Ant Design 5.x。**

Ant Design X 是专为AI应用推出的组件库，提供开箱即用的AI交互组件。

**具体例子**：
```jsx
// 【当前实现】手写对话组件
<div className="chat-container">
  {chatHistory.map(msg => (
    <div className={msg.role === 'customer' ? 'customer-bubble' : 'trainee-bubble'}>
      {msg.content}
    </div>
  ))}
  <TextArea value={inputText} onChange={setInputText} />
  <Button onClick={handleSend}>发送</Button>
</div>

// 【Ant Design X】开箱即用
import { Conversation } from '@ant-design/x';

<Conversation
  items={chatHistory.map(msg => ({
    key: msg.id,
    role: msg.role === 'customer' ? 'assistant' : 'user',
    content: msg.content
  }))}
  onSend={handleSend}
/>
```

| 功能 | 当前手写 | Ant Design X |
|------|---------|--------------|
| 对话气泡 | 手写CSS | 内置样式 |
| 流式输出 | 手写逐字追加 | `<Bubble>` 内置 streaming |
| 打字机效果 | 手写定时器 | 内置 |
| 思考链展示 | 手写折叠面板 | `<ChainOfThought>` 组件 |

**结论**：迁移到X主要是省代码量，不改变功能。当前手写实现已够用。

```
用户查询："转账失败怎么办？"

【有知识图谱】
图谱存储实体关系：
  转账失败 → 可能原因 → [限额超限, 风控触发, 账户冻结]

  1. 文档中直接提到"转账失败"的内容
  2. 无法自动扩展到关联业务
```

**结论**：有图谱能召回更全面，但当前管线已够用。暂不实现。

### 4. BGE Reranker

**当前状态：代码已实现，但默认未启用。**

Reranker的作用是对多路召回的结果重新打分排序，提升相关性。

**具体例子**：
```
用户查询："信用卡挂失手续费"

【Step 1】多路召回（20条）
向量检索 Top-10：语义相似的文档
BM25检索 Top-10：包含"挂失""手续费"关键词的文档

召回片段：
Doc 1: "信用卡挂失流程分为临时挂失和正式挂失..."（向量召回，语义相关）
Doc 2: "挂失手续费：普通卡50元，金卡免费..."（BM25召回，关键词匹配）← 精准命中
Doc 3: "信用卡年费政策说明..."（向量召回，有"费"但无关）
Doc 4: "金卡客户权益：机场贵宾厅..."（BM25召回，有"金卡"但不相关）

【Step 2】Reranker重排序（关键！）
Reranker逐一计算 (query, document) 的相关性分数：

Doc 1: score=0.65（流程相关，但没直接回答手续费）
Doc 2: score=0.92 ← 最高！直接回答手续费
Doc 3: score=0.31（讲年费，不相关）
Doc 4: score=0.25（讲贵宾厅，不相关）

重排序后 Top-5：
1. Doc 2: "挂失手续费：普通卡50元，金卡免费..." ← 精准命中！

【无Reranker（当前降级方案）】
用关键词覆盖率计算分数，效果差：
- 可能按字面匹配排序，Doc 4 排前面（因为它也有"金卡"）
- 错过了真正回答"手续费"的 Doc 2
```

**启用方式**：
```bash
# 设置环境变量启用BGE Reranker
export ENABLE_RERANKER=1
```

**结论**：建议启用。能显著提升检索准确性（预计+15-25%）。

## 三、高级检索管线

### 3.1 设计目标

从单一向量检索升级为"查询改写→多路召回→重排序→画像感知"的混合检索管线。

### 3.2 实现状态

|------|---------|---------|------|
| **查询改写器** | DeepSeek-V3 | ✅ 已实现 | 将口语化提问分解为结构化检索词 |
| **向量检索** | ChromaDB + BGE-M3 | ✅ 已实现 | 语义相似度检索 |
| **BM25 检索** | Whoosh | ✅ 已实现 | 关键词精确匹配 |

#### 3.4.2 图谱构建流程

```
Step 1: 实体抽取（用LLM）
─────────────────────────────
输入：知识库文档
输出：实体列表
  - 转账失败（业务事件）
  - 风控触发（原因）
  - 限额超限（原因）
  - 客户安抚（话术）
  - 账户查询（关联业务）

Step 2: 关系抽取（用LLM）
─────────────────────────────
输出：实体关系
  - (转账失败) → 可能原因 → (风控触发)
  - (转账失败) → 可能原因 → (限额超限)
  - (转账失败) → 关联业务 → (账户查询)
  - (转账失败) → 客户话术 → (客户安抚)

Step 3: 写入Neo4j
─────────────────────────────
Cypher语句：
CREATE (e1:Event {name: '转账失败'})
CREATE (e2:Reason {name: '风控触发'})
CREATE (e1)-[:可能原因]->(e2)
...
```

#### 3.4.3 图谱查询示例

```cypher
// 查询"转账失败"的所有关联实体
MATCH (e:Event {name: '转账失败'})-[r]-(related)
RETURN e, r, related

// 查询两跳内的所有关联业务
MATCH (e:Event {name: '转账失败'})-[*1..2]-(related)
WHERE related:Business
RETURN related.name
```

#### 3.4.4 集成到检索管线

```python
# 在 retrieval_pipeline.py 中添加图谱检索
async def graph_search(self, query: str, top_k: int = 5) -> List[Dict]:
    """图谱关联检索"""
    # 1. 从查询中识别实体
    entities = await self._extract_entities(query)

    # 2. 查询图谱获取关联节点
    cypher = """
    MATCH (e {name: $entity})-[r]-(related)
    RETURN related.name as name, type(r) as relation
    LIMIT $top_k
    """

    # 3. 返回关联文档ID
    results = []
    for entity in entities:
        nodes = neo4j_session.run(cypher, entity=entity, top_k=top_k)
        results.extend([n['name'] for n in nodes])

    return results
```

#### 3.4.5 性能影响

| 方面 | 影响 |
|------|------|
| **查询速度** | 毫秒级，比向量检索还快 |
| **内存占用** | Neo4j服务约500MB |
| **构建成本** | 一次性LLM调用（约30-60分钟处理全量文档） |

**结论**：知识图谱查询本身很快，主要成本在图谱构建（一次性工作）。
