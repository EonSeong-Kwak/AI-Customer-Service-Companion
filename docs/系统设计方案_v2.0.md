# 银行智能客服陪练系统 V2.0 设计方案

## 一、 V2.0 演进目标与核心原则
在 V1.0 成功跑通“学、练、考、评”闭环（基于单一模型与纯 Prompt 驱动）的基础上，V2.0 将引入**教学法内核（Teaching Methodology）**与**业务仿真控制（Business Simulation Control）**，从一个“聊天机器人”全面升级为“企业级沉浸式智能陪练平台”。

**核心原则**：
1. **柔性状态机强控**：引入 LLM-driven State Machine，保证模拟考试的流程走向（考点必达），同时兼容客户自然发散的话题跳转。
2. **教学理论落地**：将费曼学习法、番茄工作法、PBL（项目制学习）与反循环机制，精准落位于系统的不同阶段。
3. **闭环与自动化**：通过错题本数据流转，实现“考暴露问题 -> 练解决问题”的闭环；通过 LLM 自动生成题库，极大降低教研成本。

## 二、 核心教学机制落地架构

### 1. 【学】模块：Doc Agent + 费曼学习法 + 番茄工作法
*   **定位**：高压输入与强制消化。
*   **前端交互设计（沉浸式学练体验）**：
    *   **番茄钟机制**：学员进入学习大厅后，启动 25 分钟的“专注倒计时”。专注期内，前端锁定界面以防分心。
    *   **伴随式 AI 导师（悬浮窗按需呼出）**：摒弃主动弹出的打断式交互，采用按需呼出的悬浮窗设计（例如右下角悬浮按钮结合 Drawer 抽屉）。学员在查阅业务文档遇到难点时，可主动点击唤醒 AI 导师（Doc Agent）进行提问，用完即收起，最大程度保障无干扰的阅读体验。
*   **后端流转设计（费曼挑战）**：
    *   25 分钟结束时，触发后端路由切换：Doc Agent 切换系统提示词，进入 `Intern_Mode`（实习生模式）。
    *   **LLM 行为**：“师傅，你刚才看了《大额转账规定》，你能不能用自己的话给我讲一遍？如果不核实身份会有什么后果？”
    *   **通关判定**：只有当 LLM 评估学员的解释“通俗易懂且逻辑正确”时，番茄钟才算真正完成并结算学分。

### 2. 【考】模块：Persona Agent + PBL 项目制 + 柔性状态机
*   **定位**：连贯场景实战，解决真实问题，暴露深层弱点。
*   **数据结构升级（PBL 剧本表）**：
    *   新增 `Project` 表（如：《处理被骗老年客户追回资金》专项）。
    *   每个 Project 包含多个 `Node`（节点）：接听安抚 -> 获取账号 -> 紧急冻结 -> 报警引导。
*   **柔性状态机与黑板机制（核心架构）**：
    *   **多任务栈（Stack）**：系统为本次考试初始化必修任务栈。
    *   **LLM 幕后裁判**：每轮对话生成前，后端调用极轻量的 LLM Router，评估考生上句话是否完成了当前 Node 的目标（如：是否拿到了账号）。
    *   **抗分支干扰**：如果客户中途转移话题（如突然问余额），状态机将“查余额”压入任务栈。查完后，状态机强控 LLM 返回主线：“对了，刚才那个转账失败的事还没说完呢。”

### 3. 【练】模块：Quiz Agent + 反循环机制
*   **定位**：针对弱点的刻意练习。
*   **错题画像（User Weakness）**：
    *   Scorer Agent 在 V1.0 的“五维评分（准确、合规、态度、共情、控场）”基础上，如果发现某项（如合规性）极低，自动向 `user_weakness` 表写入标签。
*   **动态出题（反循环推送）**：
    *   次日进入练习中心时，Quiz Agent 读取该学员的弱点标签。
    *   系统利用 LLM 自动检索知识库，拼装 Prompt：“针对『账户冻结未核实身份』这个错点，生成一道全新的诈骗情景题。”
    *   打破机械背诵，强制学员在不同场景下反复练习同一薄弱点。

## 四、 数据库实体关系 (ER) 演进

在 V1.0 的基础上，新增以下核心表结构：

1. **`Project` (PBL项目表)**
   - `id`: 项目ID
   - `title`: 项目名称 (e.g., 涉诈资金拦截)
   - `description`: 项目背景描述
2. **`ProjectNode` (剧本节点表)**
   - `id`: 节点ID
   - `project_id`: 关联项目
   - `sequence_order`: 节点顺序
   - `task_goal`: 节点过关目标 (交由 LLM 裁判评估)
   - `persona_prompt`: 当前节点下客户的人格设定与情绪状态
3. **`UserWeakness` (错题画像表)**
   - `id`: 记录ID
   - `trainee_id`: 关联用户
   - `weak_dimension`: 薄弱维度 (如: compliance)
   - `source_exam_id`: 暴露该弱点的考试记录ID
   - `status`: 状态 (未解决/已攻克)
4. **`PracticeRecord` (专项练习记录表)** *(V1.0后期已实现)*
   - `id`: 记录ID
   - `question_id`: 关联题库
   - `trainee_answer`: 学员原话
   - `ai_evaluation`: AI 极简点评

## 五、 统一知识库与题库数据结构 (Auto-Builder 核心模型)

为了支持 V3.0 的“教研自动化（一键生成题库）”以及 RAG 检索的准确性，必须将“文档知识”与“练习题库”统一在一个标准的底层结构下，即 **知识原子（Knowledge Node）**。该结构是 LLM 从外部文档（PDF/Word）提取信息后输出的标准 JSON Schema，也是数据库落盘的核心依据。

### 1. 结构设计理念
- **单一数据源 (SSOT)**：RAG 检索时读取 `rule_content`（业务规则），而 Quiz Agent 抽取题目时读取 `derived_questions`，两者通过 `node_id` 强绑定。
- **面向大模型友好**：字段设计必须符合 LLM Function Calling 的抽取直觉。

### 2. 标准 JSON Schema 定义
```json
{
  "knowledge_nodes": [
    {
      "node_id": "自动生成的唯一ID",
      "category": "密码重置与找回",
      "title": "手机银行登录密码重置",
      "keywords": ["手机银行", "登录密码", "忘记密码", "人脸识别"],
      "rule_content": "支持线上自助找回。客户需验证人脸、预留手机号及名下任意本行卡号。",
      "derived_questions": [
        {
          "scenario": "哎呀，我手机银行密码忘了，登录不进去了，这可怎么办呀？",
          "reference_answer": "您好，手机银行登录密码遗失，您可以在APP登录页面点击“忘记密码”，通过人脸识别和绑定手机号验证后自助重置，重置后立即生效。",
          "key_points": ["安抚情绪", "引导APP端操作", "说明验证要素(人脸、手机号)"]
        }
      ]
    }
  ]
}
```

### 3. 数据流转说明 (Data Flow)
1. **解析阶段**：文档经 PDF/Word 解析器切割成文本块（Chunk）。
2. **抽取阶段**：Auto-Builder Agent (LLM) 吞吐文本块，输出上述 JSON 格式的数据。
3. **人机协同阶段**：JSON 数据进入“教研草稿箱”，管理员在前端微调话术与 `key_points`。
4. **入库阶段**：审核通过后，`knowledge_nodes` 存入 RAG 向量库 / 关系型表，`derived_questions` 自动拆解并写入 `questions` 题库表，建立一对多关联。

## 六、 V2.0 第一阶段实施计划建议

为平稳过渡，建议 V2.0 按照以下顺序迭代：

1. **Phase 1: 基础设施与前端体验升级 (V1.5)**
   - 实现细粒度日志落盘系统（分离 access, llm, error 日志）。
   - 前端引入全局“番茄钟”组件，提升学习仪式感。
   - 升级前端对话气泡，支持 Markdown 渲染和专业级 UI。
   - 后端 Doc Agent 新增“费曼反问”系统指令与拦截逻辑。
2. **Phase 2: 教研自动化与弱点闭环 (V3.0)**
   - 实现后台“一键生成题库”功能（Auto-Builder 自动解析文档造题）。
   - 实现 `UserWeakness` 表打标，并在“练习中心”首页增加“针对性弱点特训”入口。
   - 完善管理员端全景数据报表大屏和考试发卷配置。
   - 实现初步的 RBAC 权限隔离（区分 Trainer 学员端 与 Admin 教研端 的登录与接口权限）。
3. **Phase 3: 柔性状态机与 PBL 剧本 (V4.0)**
   - 搭建多任务栈（Task Stack）管理框架。
   - 实现后台的 LLM 幕后裁判逻辑，确保剧本在客户发脾气或转移话题时，仍能被拽回主线。
   - 实现评分规则权重动态配置。
